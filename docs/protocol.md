# Preconf demo protocol v1

This is the demo API contract. Examples use placeholders
for transaction bytes, hashes, addresses, and signatures.

## Model

One ordinary Ironwood transaction pays the merchant and a shielded service fee. The
merchant checks its own output; the service decrypts and checks its fee output.
The ordinary network transaction fee is separate from the service fee.

The demo accepts only non-coinbase v6 transactions with Ironwood spends/outputs
and no transparent, Sapling, or Orchard-pool components. Payments, service fees,
change, and revenue-sharing payouts use Ironwood. Bootstrap funding is separate
from admission. Activate NU6.3 on all regtest nodes before running the scenarios.
Ironwood reuses Orchard receivers; check the transaction's pool, not just its
address encoding. Keep witnesses and nullifier reservations in Ironwood state.

Acceptance means the service has validated the transaction, reserved its spends,
persisted it in its pending set, and signed a receipt. It does not mean miners
have fetched it or that inclusion is guaranteed. No inclusion deadline, insurance,
slashing, or miner acknowledgements in this demo.

Miners fetch the current set of accepted, still-pending transactions. Each accepted
transaction included in a block earns its miner a share of that transaction's
service fee. The fetched set has no identity, version, or inclusion requirement.

## Common types

- `txid` and block hashes: lowercase 64-character hex in node RPC display order.
- `raw_tx`: hex of the consensus-serialized transaction. Derive its txid with
  Zakura's transaction library, not a generic hash of these bytes.
- Amounts: integer zatoshis represented as decimal strings; never floats.
- `chain_id`: a random 32-byte lowercase hex identifier generated by the devnet
  launcher, shared in configuration and changed on a devnet reset. This separates
  runs even when their regtest genesis hashes are identical.
- Heights and confirmations: JSON integers. Null means absent; do not omit fields.

## Merchant API

JSON-RPC 2.0 over HTTP `POST /`, named parameters only. Three methods; no batches
or notifications in the demo. Bind to loopback or the private test network.

### `preconf_info`

Request: `{"jsonrpc":"2.0","id":1,"method":"preconf_info","params":{}}`

Result:

```json
{
  "protocol_version": 1,
  "chain_id": "<devnet-id>",
  "service_pubkey": "<32-byte-ed25519-public-key-hex>",
  "fee_address": "<service-shielded-address>",
  "min_fee_zat": "10000",
  "ready": true,
  "tip": {"height": 100, "hash": "<block-hash>"}
}
```

`10000` is a configurable demo default. `ready` requires initialized wallet,
chain reconciliation, and available admission capacity checks; `tip` is null
before chain initialization. Clients pin the public key and chain ID from the
launcher configuration; fetching this method alone is not key authentication.

### `preconf_submit`

```json
{"jsonrpc":"2.0","id":2,"method":"preconf_submit","params":{"raw_tx":"<transaction-hex>"}}
```

Returns the same result shape as `preconf_get` below, initially `pending`.
The receipt is the merchant's preconfirmation. There is no separate quote,
invoice, fee transaction, or merchant registration.

Before returning success, the service must:

1. Decode and consensus-validate against the current chain, including proofs,
   anchors, expiry, and spent inputs/nullifiers. For this demo, require confirmed
   inputs and reject dependencies on other unconfirmed transactions.
2. Decrypt service outputs and sum their values; require at least `min_fee_zat`.
3. Reject conflicts with another accepted pending transaction. Reserve its
   Ironwood nullifiers.
4. Check that the complete pending set fits the configured response size cap.
   Each transaction must fit a valid block template with coinbase headroom;
   the entire pending set need not fit in one block.
5. Atomically persist the reservation, transaction, fee, and receipt.
   Serialize admission with chain updates and other submissions.

Ordinary mempool conflict policy must not veto an otherwise valid admission.
The miner integration needs a separate priority transaction store and validation
path. An already chain-spent input must still be rejected.

Retries for the same accepted transaction return its existing receipt and current
status, with no new fee or reservation. Check duplicates before new-admission checks.
The service distributes accepted transactions through P2P; it need not first
submit them to the ordinary mempool. Rejected transactions receive no receipt.

### `preconf_get`

```json
{"jsonrpc":"2.0","id":3,"method":"preconf_get","params":{"txid":"<txid>"}}
```

Result (also returned by submit):

```json
{
  "txid": "<txid>",
  "status": "pending",
  "receipt": {"payload": "<base64>", "signature": "<64-byte-ed25519-signature-hex>"},
  "inclusion": null,
  "failure_reason": null
}
```

Statuses: `pending`, `included`, `failed`. Included sets `inclusion` to
`{"block_hash":"<hash>","height":101,"confirmations":1}`. Failed sets
`failure_reason` to `conflict`, `expired`, or `invalidated` and inclusion to null.
Pending has both fields null. Confirmations are relative to the current best
chain; these statuses can change after a reorg. A receipt is immutable history,
not a signature over this mutable status response.

### Receipt

Sign `UTF8("zcash-preconf-demo/v1\n") || base64_decode(payload)` with Ed25519.
The decoded payload is a UTF-8 JSON object:

```json
{"chain_id":"<devnet-id>","txid":"<txid>","service_fee_zat":"10000"}
```

Generate these bytes once and persist them with the signature. Verification uses
the exact decoded bytes, never reserialized JSON. Reject duplicate JSON keys;
check all fields against the expected chain and transaction. Standard padded
Base64. Merchants must also verify their payment output independently.

### Errors

Use standard JSON-RPC parse/request/method/parameter errors. Application errors
have `error.data.reason` from this table:

| Code | Reason | Meaning |
| --- | --- | --- |
| -32001 | `not_ready` | Chain/wallet not ready; retry later |
| -32002 | `invalid_tx` | Invalid, expired, already mined, or unconfirmed dependency |
| -32003 | `fee_too_low` | No sufficient decryptable service fee |
| -32004 | `conflict` | Another accepted transaction reserves the spend |
| -32005 | `pending_full` | Admission would exceed the pending response size cap |
| -32006 | `not_found` | Unknown txid |

An internal persistence failure returns standard internal error `-32603`, never
an acceptance. If the reply is lost after commit, retrying recovers the receipt.

## Miner P2P API

One custom service on Zakura v2 QUIC, using the current `RequestResponseService`
interface. The miner pins the singleton server's transport peer identity in its
configuration. No HTTP miner endpoint and no separate signatures on the pending set.

Demo assignments (reserve in the custom branch; not a global allocation):

| Field | Value |
| --- | --- |
| Service name | `zakura.preconf.v1` |
| Capability | `1 << 17` |
| Stream kind / version | `65` / `1` |
| Stream mode | `RequestResponse` |
| Message 0 | `GetPending` |
| Message 1 | `Pending` |
| Message 2 | `Error` |

Each request and response is one native transport frame, flags zero, payload
UTF-8 JSON. Use transport request correlation; no extra request ID. The service's
frame cap is 2 MiB plus the 8-byte frame header; the entire encoded response must also fit negotiated frame
and message limits. No chunking. Limit the serialized Pending JSON to 2 MiB,
including metadata, and RPC request bodies to 2 MiB. Reject new admissions
before exceeding these bounds. A peer with insufficient negotiated capacity gets
`{"reason":"capacity"}` or a stream reset if even that response cannot fit.

`GetPending` (message 0):

```json
{"chain_id":"<devnet-id>"}
```

`Pending` (message 1):

```json
{
  "chain_id": "<devnet-id>",
  "tip": {"height": 100, "hash": "<block-hash>"},
  "transactions": ["<raw-tx-hex>", "<raw-tx-hex>"]
}
```

The response is an atomic snapshot: tip and pending set describe the same chain
view.
Transactions are in acceptance order. An empty set returns `transactions: []`.
Only durably accepted transactions may be returned.

`Error` (message 2): `{"reason":"not_ready"}`. Other reasons are `wrong_chain`
and `capacity`. Malformed payloads, unknown message types, or nonzero flags reset
the request stream. Unknown versions are rejected by transport negotiation.

Miners poll every 500 milliseconds and revalidate on a new chain tip, with one outstanding request
and a two-second timeout. No push, deltas, subscriptions, or historical fetch.
An error does not mean an empty pending set: retain the last valid snapshot and
revalidate against the local chain. Log stale fetches. On startup without a
snapshot, mining may continue normally; there is no availability guarantee.

### Template rule

Decode and validate service transactions against the miner's own template parent.
Add valid service transactions first in acceptance order, as block limits allow,
then fill remaining space from the ordinary mempool, excluding conflicts with
still-valid service transactions and their dependent transactions. Ignore service
transactions already mined; skip invalid/expired ones and log why. Never bypass
consensus checks. Leave transactions that do not fit pending for a later block.
Refresh cached templates when the fetched transaction set changes.

Mempool arrival order and a higher conflicting transaction fee must not defeat
service transaction priority. Keeping raw service transactions outside the ordinary mempool
is essential to this rule. Blocks built by other miners remain normally valid.

## Inclusion and the 98% payout

For each new best-chain block, intersect its txids with accepted transactions.
Record their inclusion block and remove them from the pending set. Mark accepted
transactions whose spends were consumed by a different transaction as failed.
Revalidate the rest and update merchant statuses.

Persist acceptance, service fee, inclusion, and payout assignment per txid.
Pay only for accepted fee-bearing transactions actually included, regardless of
which P2P response the miner fetched. A block with no such transactions earns no
service payout. Transactions left out remain pending and can earn a later miner
their fee share.

For v1, enable revenue sharing only for configured Ironwood coinbase receivers.
Give each demo miner a distinct receiver and pay its revenue share to that same
receiver in the Ironwood pool. Recover Ironwood coinbase outputs using the public
all-zero outgoing viewing key and the Ironwood note-encryption domain. Match the
decoded recipient receiver, not a unified-address string. Ignore zero-value
padding outputs. Attribute a block only when positive-value outputs match exactly
one configured miner; multiple outputs to that same miner are fine.

No miner viewing/spending keys, self-reported miner ID, or payout claim over P2P.
Unknown, unsupported, or ambiguous recipients are recorded as unattributed; hold
their payout and log why. Their blocks still receive normal consensus validation
and their included payments still update merchant status. This is attribution
for controlled demo miners, not adversarial authentication.

Shielded coinbase does not use Sprout. After NU6.3, Sapling and Ironwood coinbase
outputs are permitted and shielded coinbase outputs must be recoverable using
the all-zero outgoing viewing key: see [ZIP 213](https://zips.z.cash/zip-0213).
Supporting Sapling attribution later is possible but outside this Ironwood-only
demo. Zakura already implements Ironwood coinbase construction and recovery checks
in `zakura-rpc/src/methods/types/transaction.rs` and
`zakura-chain/src/primitives/zcash_note_encryption.rs` under the sibling repo's
`crates/` directory.

At **two total confirmations** (`tip_height - inclusion_height + 1 >= 2`), create
one payout transaction per inclusion block:

`miner_amount_zat = floor(sum(included_service_fees_zat) * 98 / 100)`

Only count accepted fees not already paid or reserved by a payout. The service
retains the remainder and pays the payout's ordinary network fee separately.
Prefund its wallet on regtest to avoid small-fee/dust and fee-selection problems.
Persist the signed payout bytes, txid, and transaction-to-payout assignments before
broadcasting to the ordinary mempool. Retry those same bytes after crashes or
broadcast timeouts; do not construct a second payment for the same assignment.

Track payout state (`waiting`, `broadcast`, `confirmed`, `blocked`) separately
from merchant status. Insufficient spendable funds leave it waiting with a reason.
An expired signed payout becomes blocked for inspection. Other broadcast failures
are logged and retried using the same bytes.

On a reorg before signing, cancel the orphaned block's unsigned payout and
reconcile reservations/statuses against the new chain. Requeue still-valid
transactions in original acceptance order. If a signed
payout's inclusion block is orphaned, mark settlement blocked and log it for
inspection; do not automatically pay again. Deep-reorg recovery is outside v1.

## Demo observability and scenarios

Structured JSON logs cover acceptance, pending-set fetches, template selection,
inclusion/conflicts, and the payout lifecycle. SQLite stores the current ledger
and timestamped events. `/state` exposes that ledger for local inspection.
`/metrics` exports readiness, chain height, transaction counts by status, and
payout counts by status. Transaction hashes stay in logs and SQLite.

`./demo.sh` launches the real nodes and automated driver, checks payments,
signed receipts, duplicate submissions, higher-fee conflicts arriving before
acceptance, service conflict rejection, both miners' payouts at two confirmations,
a rollback before signing, an outsider mining a conflict, and service restart.
It then generates ongoing payments and periodic double-spend attempts.
`./demo.sh --once` stops after the assertions. Logs and passing evidence remain
under `runs/`. See the README for endpoints and file layout.

`./live.sh` runs the persistent explorer and randomized 20–40 payment batches.
Grafana, latency histograms, and adversarial coinbase-attribution scenarios remain
follow-up work.
